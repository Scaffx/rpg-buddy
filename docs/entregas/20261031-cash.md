# Quarta abertura de baú: pagamento único Paddle

## Contrato entregue

- `chest-cash-checkout` exige `Authorization: Bearer <access_token>` e confirma o usuário com `auth.getUser(token)`. `GET` retorna `{ready,reason?,already_owned,price:{currency:"BRL",amount_minor:990},order_id?,order_status?,request_id?}`. O `request_id` existente permite retomar um pedido `ready` em outro navegador sem criar outro. `POST` exige `{request_id:UUID}`; quando o pedido está anexado à transação, retorna `{ready:true,order_id,request_id,transaction_id,replayed}`. O cliente abre `Paddle.Checkout.open({transactionId})` com a inicialização Paddle existente, sem conceder o benefício pelo callback. [Paddle: transação em checkout](https://developer.paddle.com/build/transactions/pass-transaction-checkout/).
- `POST` com uma criação Paddle de resultado incerto retorna HTTP 202, `{ready:false,reason:"ORDER_PENDING_RECONCILIATION",order_id}`. A nova tentativa com o mesmo `request_id` **não cria outra transação**. Um pedido `ready` devolve o mesmo `transaction_id`; um pedido `creating` exige reconciliação operacional. Isso evita uma segunda cobrança automática quando a resposta do provedor se perde. A API Paddle não documenta chave de idempotência arbitrária para `POST /transactions`; o bloqueio é local e durável.
- O webhook aceita somente `transaction.completed`, verifica HMAC SHA-256 sobre `ts:rawBody` em até cinco segundos e consulta a API Paddle para ler a transação atual. Eventos `paid`/`updated` não liberam nada. A assinatura segue a [documentação oficial de verificação](https://developer.paddle.com/webhooks/about/signature-verification/).
- A liberação exige pedido conhecido por `transaction_id`, usuário e ID do pedido em `custom_data` correspondentes, preço ativo avulso, BRL 990, imposto incluso, quantidade 1, transação `completed` de origem API e sem assinatura, desconto ou crédito. O valor final é conferido em `details.totals.total`, que a [API Paddle trata como fonte de verdade](https://developer.paddle.com/api-reference/transactions/get-transaction/). O banco finaliza pedido e recibo na mesma transação por RPC restrita a `service_role`; `custom_data` sozinho não concede nada.
- Os webhooks existentes de assinatura mensal/anual e o preço existente não foram alterados. A quarta abertura é permanente e só aparece após as duas ampliações por ouro, conforme a migração de baús anterior.

[Configuração de checkout Paddle](https://developer.paddle.com/paddle-js/methods/paddle-checkout-open/). Testar totais BRL 9,90 com imposto incluso nas regiões suportadas. Caso algum checkout produza total diferente, o webhook recusa o benefício e o pedido deve ser tratado operacionalmente antes de ativar para usuários.
5. Disponibilizar reconciliação operacional para pedidos `creating` após falha de rede; não reexecutar automaticamente `POST /transactions`. O operador consulta o pedido privado pelo `order_id` e busca transações Paddle live de `origin=api` no intervalo de criação, paginando até cobrir a janela. Para cada candidato, confirma via `GET /transactions/{id}`: `custom_data` com o mesmo pedido/usuário, preço avulso, BRL 990, quantidade 1 e sem assinatura. Só após encontrar **uma** correspondência independente pode anexar o ID com `attach_adventure_chest_cash_transaction` usando `service_role`; se estiver `draft`/`ready`, o mesmo `request_id` retorna o `transaction_id` existente. Se já estiver `completed`, reentregar o evento Paddle `transaction.completed` assinado para o webhook depois do anexo, sem inventar um ID de evento. Com zero ou múltiplos candidatos, o pedido continua bloqueado para análise e nenhuma nova transação deve ser criada. O endpoint [lista transações por origem](https://developer.paddle.com/api-reference/transactions/list-transactions/) e o [GET da transação](https://developer.paddle.com/api-reference/transactions/get-transaction/) são as fontes da inspeção. **Esse procedimento ainda não está automatizado nem validado contra Paddle e é gate de ativação live**; a UI deve comunicar pedido pendente em vez de prometer retomada imediata.
